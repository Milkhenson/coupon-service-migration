# SRS v1.0  Спецификация требований к сервису купонов

## 1. Назначение и рамки

Документ фиксирует функциональные и нефункциональные требования к сервису купонов
при выносе из монолита в отдельный микросервис с миграцией из БД Oracle в PostgreSQL.
Интеграции проектируются заново. Документ - основа для модели данных, контрактов API
и архитектуры (C4). Версия v1.0: все критичные вопросы закрыты ответами ментора;
оставшиеся допущения  в [06-assumptions.md](06-assumptions.md).

## 2. Контекст и цель

- Сервис купонов работает на Oracle, переносится в PostgreSQL как отдельный микросервис.
- Высоконагруженная система: пик 2000 активаций/сек, 400 гашений/сек, 1000 входящих
  запросов/сек на гашение; SLA гашения 5–10 сек - синхронно, активации 40 сек-1 мин -
  допускает асинхронность.
- Интеграции: загрузка акций ETL каждые 15 минут; выгрузка в DWH ежедневно - часть пачками, часть Kafka streaming.
- Экран ручных массовых операций менеджера: до 200 000 купонов за операцию,
  асинхронная обработка.
- Сервис купонов не только проверяет ключи касс, но и генерирует/выдаёт их
25-го числа ночью, на следующий месяц.
- Хранимые процедуры и триггеры не переносятся, логика в бэкенде.

## 3. Роли и участники

| Роль | Описание | Взаимодействие |
|---|---|---|
| Касса (POS) | Любой тип (с кассиром, самообслуживание), для сервиса непринципиально | API по внутреннему каналу |
| Кассир | Применяет купон/инициирует восстановление купона | Опосредованно через кассу |
| Покупатель | Получает купон, предъявляет к гашению | Опосредованно через кассу |
| Менеджер | Ручные массовые операции; ~20 человек, параллельно максимум двое | Экран ручных операций + API |
| Сотрудник поддержки касс | Разбор статуса E по запросу менеджера; массовое гашение при подозрении на слив (антифрод) | Внутренний интерфейс |
| Сотрудник антифрода | Инициирует массовое гашение при сливе; источник сигнала - вне сервиса | Через поддержку/менеджера |
| Система акций (внешняя) | Источник акций, торговых точек, дат | ETL каждые 15 минут |
| Data engineers | Отвечают за ETL-загрузку акций | Эксплуатация ETL |
| DWH компании | Получатель купонов и событий | Ежедневная выгрузка + Kafka streaming |

## 4. Функциональные требования (ФТ)

### ФТ-1. Активация купона

Сервис должен активировать купон по запросу кассы: принять номер купона, акцию активации, код торговой точки (далее ТТ) и номер кассы, присвоить купону статус A и зафиксировать событие ACTIVATE. Сервис должен поддерживать асинхронную обработку активаций пачками: при коротком перерыве связи в пределах смены касса накапливает активации в локальном буфере и досылает их после успешной авторизации; сервис принимает пачку в очередь и обрабатывает её асинхронно. Для асинхронной обработки активаций должен использоваться брокер сообщений.

### ФТ-2. Проверка купона перед гашением

Сервис должен по запросу кассы синхронно проверить возможность гашения купона: номер купона, ТТ, номер кассы и вернуть перечень акций, по которым купон может быть погашен.

### ФТ-3. Гашение купона

Сервис должен синхронно гасить купон по запросу кассы: номер купона, акция гашения, ТТ, номер кассы, переводить статус A в D и фиксировать событие REDEEM.  
Сервис должен:

- отклонять гашение купона, уже находящегося в статусе D, возвращая кассе ответ «погасить нельзя», и логировать неудачную попытку;
- отклонять гашение, если срок действия акции истёк;
- обеспечивать идемпотентность: повторный запрос с тем же ключом идемпотентности не приводит к повторному гашению.

### ФТ-4. Восстановление купона

Сервис должен восстанавливать купон и фиксировать событие RESTORE при одновременном выполнении условий: акция действует, купон находится в статусе D. Восстановление инициируется сотрудником поддержки или менеджером через систему либо запросом от кассы. После окончания срока действия акции восстановление запрещено.

### ФТ-5. Проверка и выдача ключа безопасности кассы

Сервис должен:

- проверять ключ кассы при её включении и подтверждать авторизацию на день; при неверном ключе не предоставлять подключение до отправки верного ключа;
- обеспечивать срок действия ключа — один месяц;
- выдавать кассе ключ на следующий месяц раз в месяц, 26-го числа, вместе с проверкой ключа;
- генерировать ключи для всех касс 25-го числа в ночное время;
- хранить хеш ключа; касса хранит сам ключ;
- переходный период конца месяца принимать оба ключа (текущий и следующий) по VALID_FROM/VALID_TO;
- обеспечивать SLA проверки ключа до 30 секунд при пиковой нагрузке до 200 запросов в утренние часы по МСК.

### ФТ-6. Ручные массовые операции менеджера

Сервис должен предоставлять менеджеру возможность массово активировать, гасить или восстанавливать купоны по загруженному списку номеров (Excel или ручной ввод):

- лимит до 200 000 купонов за одну операцию;
- обработка асинхронная: после постановки задачи в очередь пользователю отображается «Задача поставлена в очередь»; задача имеет статус «в очереди / выполняется / завершена»;
- валидация до применения минимальная: проверка существования купона в БД и соответствия его статуса выполняемой операции;
- предпросмотр результата не предоставляется;
- по итогам операции формируется отчёт: количество успешно изменённых купонов и количество неуспешных с указанием причин;
- функция отката операции не реализуется: откат выполняется повторной массовой операцией с нужным статусом; откат активации невозможен - обратной операции «деактивация» нет, откат гашения выполняется через восстановление;
- пагинация отображения - пользовательская: пользователь выбирает количество записей на страницу. Например, 10/50/100;
- аудит действий менеджера не ведётся.

### ФТ-7. Разбор статуса «ошибка»

Сервис должен позволять сотруднику поддержки по запросу менеджера вручную возвращать купон из статуса E в статус A или D. Операция должна логироваться в журнале событий по купонам; персональные данные сотрудника не фиксируются. Конкретный тип события для логирования разбора E — на согласовании (см. [06-assumptions.md](06-assumptions.md), Д-6).

### ФТ-8. Загрузка акций

Сервис должен получать акции, ТТ и даты их действия из системы акций пачками с периодичностью каждые 15 минут. Передача БД -> БД через ETL-движок. Состав передаваемых данных соответствует структуре таблиц акций, ТТ и дат действия.

### ФТ-9. Выгрузка в DWH

Сервис должен передавать в DWH купоны и события по купонам: часть данных пачками, часть через Kafka streaming. Допустимая задержка передачи - до суток. При недоступности DWH сервис должен после восстановления доступности передать накопленную дельту. Историю изменений ведёт DWH.

### ФТ-10. Логирование событий

Сервис должен логировать в COUPON_EVENT все события по купонам: активацию, гашение, восстановление, разбор E и неудачные попытки. Для ручных операций разбора E используется отдельный тип события. Аудит действий менеджера отдельно не ведётся; логин сотрудника не фиксируется.

### ФТ-11. Перенос структуры и данных

Сервис должен обеспечивать перенос структуры и данных из Oracle в PostgreSQL с маппингом типов; хранимые процедуры и триггеры не переносятся, логика реализуется в приложении.

### ФТ-12. Партиционирование

Таблицы COUPON и COUPON_EVENT должны быть партиционированы: COUPON - по ACTIVATION_DATE, COUPON_EVENT - по EVENT_DATE.

## 5. Нефункциональные требования (НФТ)

### НФТ-1. Производительность

Сервис должен выдерживать пиковую нагрузку: не менее 2000 активаций/сек, не менее 400 гашений/сек, не менее 100 восстановлений/сек, не менее 200 проверок ключа кассы/сек.

### НФТ-2. Конкурентность

Сервис должен выдерживать не менее 1000 входящих запросов/сек на гашение и обеспечивать защиту от двойного гашения одного купона при конкурентных запросах.

### НФТ-3. SLA времени ответа

Сервис должен обеспечивать время ответа на операции:

- активация  не более 40 сек;
- гашение  не более 10 сек;
- восстановление не более 20 сек;
- проверка ключа кассы не более 30 сек.

Целевые значения p95 и p99 рассчитываются как 0,7 и 0,8 от максимального SLA соответственно.

### НФТ-4. Доступность и отказоустойчивость

Сервис должен обеспечивать:

- доступность не ниже 98%, целевая - 99%;
- RPO: потерю данных из БД не допускать; допустима потеря только данных, не дошедших до БД;
- наличие запасных экземпляров сервиса и БД, репликацию master -> реплики.

### НФТ-5. Соединения

Сервис должен использовать пул соединений перед PostgreSQL и балансировщик нагрузки для распределения запросов.

### НФТ-6. Идемпотентность

Сервис должен обеспечивать идемпотентность операций активации и гашения по ключу идемпотентности: повторный запрос с тем же ключом не должен приводить к повторной активации или повторному гашению.

### НФТ-7. Инфраструктура и данные

Сервис должен:

- хранить данные с партиционированием COUPON по ACTIVATION_DATE и COUPON_EVENT по EVENT_DATE;
- выдерживать дисковую нагрузку с учётом особенностей PostgreSQL;
- выполнять пакетную генерацию ключей касс 25-го числа в ночное окно 22:00-07:00 МСК вне часов пик.

### НФТ-8. Безопасность

Сервис должен:

- авторизовывать кассу по ключу, передаваемому по внутреннему каналу; при неверном ключе не предоставлять подключение;
- обеспечивать срок действия ключа один месяц;
- хранить хеш ключа; касса хранит сам ключ.

### НФТ-9. Наблюдаемость

Сервис должен обеспечивать сбор и отображение метрик:

- количество запросов от касс, количество успешных/неуспешных, время обработки;
- после миграции на PostgreSQL контроль производительности БД:

- использование индексов;
- раздувание таблиц и индексов;
- ожидание блокировок при конкурентных операциях.

### НФТ-10. Совместимость типов

Сервис должен обеспечивать маппинг типов Oracle -> PostgreSQL:

- NUMBER(*,0) -> bigint;
- Oracle DATE -> timestamp(0) или timestamptz;
- пустая строка Oracle ('') → NULL;
- VARCHAR2 BYTE vs CHAR с учётом семантики длины;

хранимые процедуры и триггеры не переносятся, логика реализуется в приложении.

### НФТ-11. Гарантия доставки в DWH

Сервис должен обеспечивать доставку данных в DWH не менее одного раза at-least-once: при недоступности DWH накапливать дельту и передавать её после восстановления доступности. Допустимая задержка - до суток.

### НФТ-12. Миграция

Сервис должен обеспечивать миграцию с простоем не более 5–10 минут в окно 01:00–02:00 МСК, с параллельной работой Oracle и PostgreSQL в переходный период.

## 6. Use cases

### UC-1. Активация купона

- **Акторы:** касса (POS) - основной; кассир, покупатель - участники; сервис купонов.
- **Цель:** активировать купон при получении его покупателем и зафиксировать факт активации.
- **Предусловия:** касса авторизована в сервисе (см. [UC-5](#uc-5-проверка-ключа-кассы)).
- **Триггер:** касса печатает купон покупателю, покупка совершена.
- **Основной поток:**
  1. Касса отправляет запрос на активацию: номер купона, акция активации, ТТ, номер кассы.
  2. Сервис проверяет акцию, ТТ и дату действия.
  3. Сервис создаёт купон в статусе A, фиксирует событие ACTIVATE.
  4. Сервис возвращает кассе подтверждение активации.
- **Альтернативные потоки:**
  - A1. Асинхронная активация - офлайн-буфер. Связь с сервисом недоступна - касса копит активации в локальном буфере. При восстановлении связи касса проходит авторизацию ([UC-5](#uc-5-проверка-ключа-кассы)) и досылает пачку. Сервис принимает пачку в очередь и подтверждает приём. Сервис обрабатывает пачку асинхронно: для каждой активации из пачки проверяет акцию, ТТ и дату действия и создаёт купон в статусе A с событием ACTIVATE.
  - A2. Повторная досылка пачки. Касса не получила подтверждение приёма пачки и отправила её повторно. Сервис по ключу идемпотентности определяет, что активации уже обработаны, и не создаёт дубликаты.
- **Исключительные потоки:**
  - E1. Невалидная акция / ТТ / дата. Сервис не находит акцию или ТТ, либо дата вне действия - возвращает кассе ошибку, активация не создаётся.
  - E2. Недоступность БД. Транзакция не завершается - купон не создаётся, касса получает ошибку; при ретрае сценарий повторяется.
- **Постусловия:** при успехе купон в статусе A, событие ACTIVATE зафиксировано; при отказе купон не создан; при сбое купон не создан, возможна повторная обработка.

- **Связанные требования:** [ФТ-1](#фт-1-активация-купона), [ФТ-10](#фт-10-логирование-событий); [НФТ-1](#нфт-1-производительность), [НФТ-3](#нфт-3-sla-времени-ответа), [НФТ-6](#нфт-6-идемпотентность). UC: [UC-5](#uc-5-проверка-ключа-кассы).

### UC-2. Проверка купона перед гашением

- **Акторы:** касса (POS)- основной; кассир - участник; сервис купонов.
- **Цель:** проверить, можно ли погасить купон, и получить перечень акций, по которым это возможно.
- **Предусловия:** касса авторизована (см. [UC-5](#uc-5-проверка-ключа-кассы)).
- **Триггер:** покупатель предъявляет купон к оплате.
- **Основной поток:**
  1. Касса отправляет запрос на проверку: номер купона, ТТ, номер кассы.
  2. Сервис проверяет статус купона.
  3. Сервис проверяет действие акции на данной ТТ и дату.
  4. Сервис возвращает кассе перечень акций, по которым купон может быть погашен.
- **Альтернативные потоки:**
  - A1. Купон не найден. Сервис возвращает ответ «купон не найден».
  - A2. Купон не в статусе A. Сервис возвращает ответ «купон недоступен для гашения».
  - A3. Акция не действует на ТТ/дату. Сервис возвращает пустой перечень акций для гашения.
- **Исключительные потоки:**
  - E1. Недоступность сервиса/БД. Касса получает ошибку; при ретрае сценарий повторяется.
- **Постусловия:** статус купона не изменяется; касса получила результат проверки.

- **Связанные требования:** [ФТ-2](#фт-2-проверка-купона-перед-гашением); [НФТ-3](#нфт-3-sla-времени-ответа) UC: [UC-3](#uc-3-гашение-купона), [UC-5](#uc-5-проверка-ключа-кассы).

### UC-3. Гашение купона

- **Акторы:** касса (POS) - основной; кассир, покупатель - участники; сервис купонов.
- **Цель:** погасить купон, применить скидку и получить однозначный результат в момент операции.
- **Предусловия:** касса авторизована ([UC-5](#uc-5-проверка-ключа-кассы)); купон существует; выполнена проверка ([UC-2](#uc-2-проверка-купона-перед-гашением)).
- **Триггер:** кассир инициирует гашение купона.
- **Основной поток:**
  1. Касса отправляет запрос: номер купона, акция гашения, ТТ, номер кассы, ключ идемпотентности.
  2. Сервис проверяет ключ идемпотентности.
  3. Сервис проверяет купон: существует, статус A, акция действует на ТТ и дату.
  4. Сервис переводит A -> D, фиксирует событие REDEEM (правила перехода — см. [раздел 7](#7-бизнес-правила-и-статусная-модель)).
  5. Сервис возвращает кассе синхронный ответ «погашено».
  6. Касса применяет скидку.
- **Альтернативные потоки:**
  - A1. Купон уже погашен. Сервис возвращает «погасить нельзя», логирует неудачную попытку, статус не меняется.
  - A2. Срок действия акции истёк. Сервис возвращает «погасить нельзя», статус не меняется.
  - A3. Повторный запрос с тем же ключом идемпотентности. Сервис возвращает тот же результат, что и при первом запросе, без повторного изменения статуса.
- **Исключительные потоки:**
  - E1. Таймаут. Касса не получила ответ — повторяет запрос (до 3 ретраев) с тем же ключом; при отсутствии ответа после 3 ретраев показывает ошибку.
  - E2. Недоступность БД / сбой. Транзакция откатывается, купон остаётся в A; касса получает ошибку, ретрай безопасен.
  - E3. Конкурентное гашение с двух касс. Один запрос переводит A -> D, второй получает «погасить нельзя»; второй логируется как неудачная попытка.
- **Постусловия:** при успехе купон в D, событие REDEEM, касса получила «погашено»; при отказе статус не изменён, попытка залогирована; при сбое статус A (откат) или E (неопределённое состояние, разбор — [UC-8](#uc-8-разбор-статуса-e)).

- **Связанные требования:** [ФТ-3](#фт-3-гашение-купона), [ФТ-2](#фт-2-проверка-купона-перед-гашением), [ФТ-10](#фт-10-логирование-событий); [НФТ-2](#нфт-2-конкурентность), [НФТ-3](#нфт-3-sla-времени-ответа), [НФТ-6](#нфт-6-идемпотентность)  UC: [UC-2](#uc-2-проверка-купона-перед-гашением), [UC-5](#uc-5-проверка-ключа-кассы), [UC-8](#uc-8-разбор-статуса-e).

### UC-4. Восстановление купона

- **Акторы:** касса / менеджер / сотрудник поддержки - основной; кассир, покупатель - участники; сервис купонов.
- **Цель:** вернуть купон из статуса D в A, чтобы покупатель мог использовать его позже.
- **Предусловия:** купон в статусе D; акция действует.
- **Триггер:** покупатель передумал / сбой на кассе / либо ручная операция менеджера/поддержки.
- **Основной поток:**
  1. Инициатор отправляет запрос на восстановление: номер купона.
  2. Сервис проверяет: купон в статусе D, акция действует.
  3. Сервис переводит D -> A, фиксирует событие RESTORE (правила перехода — см. [раздел 7](#7-бизнес-правила-и-статусная-модель)).
  4. Сервис возвращает подтверждение.
- **Альтернативные потоки:**
  - A1. Купон не в статусе D. Сервис возвращает «восстановление невозможно».
  - A2. Срок действия акции истёк. Сервис возвращает «восстановление невозможно».
- **Исключительные потоки:**
  - E1. Недоступность БД / сбой. Транзакция откатывается, статус не меняется; повторный запрос безопасен.
- **Постусловия:** при успехе купон в A, событие RESTORE; при отказе статус не изменён.

- **Связанные требования:** [ФТ-4](#фт-4-восстановление-купона), [ФТ-10](#фт-10-логирование-событий); [НФТ-6](#нфт-6-идемпотентность) UC: [UC-3](#uc-3-гашение-купона).

### UC-5. Проверка ключа кассы

- **Акторы:** касса (POS) - основной; сервис купонов.
- **Цель:** авторизовать кассу на день и выдать ключ на следующий месяц.
- **Предусловия:** ключ сгенерирован сервисом (см. [UC-6](#uc-6-генерация-ключей)).
- **Триггер:** включение кассы или проверка в середине дня.
- **Основной поток:**
  1. Касса отправляет ключ, код ТТ, номер кассы.
  2. Сервис проверяет ключ по VALID_FROM/VALID_TO.
  3. Сервис подтверждает авторизацию кассы на день.
  4. Раз в месяц 26-го числа вместе с подтверждением сервис выдаёт кассе ключ на следующий месяц.
- **Альтернативные потоки:**
  - A1. Неверный ключ. Сервис не предоставляет подключение до отправки верного ключа.
  - A2. Проверка в середине дня. Касса отправляет запрос повторно, сервис проверяет ключ по той же схеме - шаги 2-3.
- **Исключительные потоки:**
  - E1. Недоступность сервиса. Касса получает ошибку; повторяет проверку при следующем подключении.
- **Постусловия:** при успехе касса авторизована на день; 26-го числа получила ключ на следующий месяц; при неверном ключе подключение не предоставлено.

- **Связанные требования:** [ФТ-5](#фт-5-проверка-и-выдача-ключа-безопасности-кассы); [НФТ-3](#нфт-3-sla-времени-ответа) UC: [UC-6](#uc-6-генерация-ключей).

### UC-6. Генерация ключей

- **Акторы:** сервис купонов - основной.
- **Цель:** сгенерировать ключи на следующий месяц для всех касс.
- **Предусловия:** наступило 25-е число, ночное окно 22:00–07:00 МСК.
- **Триггер:** плановый запуск пакетной задачи 25-го числа.
- **Основной поток:**
  1. Сервис запускает генерацию ключей для всех касс.
  2. Для каждой кассы генерируется ключ на следующий месяц.
  3. Сохраняется хеш ключа с VALID_FROM - 1-е число следующего месяца- и VALID_TO - конец месяца.
  4. Задача завершается, фиксируется результат.
- **Альтернативные потоки:**
  - A1. Частичная генерация. Часть касс не обработана
  задача фиксирует список необработанных, выполняется повторный запуск.
- **Исключительные потоки:**
  - E1. Сбой задачи. Генерация прерывается, фиксируется ошибка; выполняется повторный запуск в том же ночном окне.
- **Постусловия:** при успехе ключи на следующий месяц сгенерированы и сохранены для всех касс; при сбое - частичная генерация, требуется повторный запуск.

- **Связанные требования:** [ФТ-5](#фт-5-проверка-и-выдача-ключа-безопасности-кассы); [НФТ-7](#нфт-7-инфраструктура-и-данные) UC: [UC-5](#uc-5-проверка-ключа-кассы).

### UC-7. Ручные массовые операции

- **Акторы:** менеджер / сотрудник поддержки - основной; сервис купонов, брокер.
- **Цель:** массово активировать, погасить или восстановить купоны по загруженному списку.
- **Предусловия:** пользователь авторизован; список номеров подготовлен - Excel или ручной ввод.
- **Триггер:** пользователь загружает список и выбирает действие.
- **Основной поток:**
  1. Пользователь загружает список и выбирает действие.
  2. Сервис ставит задачу в очередь, показывает «Задача поставлена в очередь».
  3. Сервис асинхронно обрабатывает задачу: валидация - существует купон, подходящий статус.
  4. Сервис применяет операцию к валидным купонам.
  5. Сервис формирует отчёт: успешно / неуспешно с причинами.
  6. Пользователь видит отчёт по итогам.
- **Альтернативные потоки:**
  - A1. Превышен лимит. Список больше 200 000, сервис отклоняет загрузку с сообщением о лимите.
  - A2. Часть купонов не прошла валидацию. Невалидные купоны не применяются, попадают в отчёт с причинами.
  - A3. Откат операции. Пользователь повторно запускает массовую операцию с нужным статусом (откат активации невозможен; откат гашения через восстановление).
- **Исключительные потоки:**
  - E1. Задача упала. Фиксируется ошибка, пользователь видит статус «завершена с ошибкой»; возможен повторный запуск.
- **Постусловия:** при успехе операция применена к валидным купонам, отчёт сформирован; при частичном успехе применено к валидным, невалидные в отчёте; при сбое операция не применена (или частично), зафиксирована ошибка.

- **Связанные требования:** [ФТ-6](#фт-6-ручные-массовые-операции-менеджера), [ФТ-10](#фт-10-логирование-событий) UC: [UC-8](#uc-8-разбор-статуса-e).

### UC-8. Разбор статуса E

- **Акторы:** сотрудник поддержки - основной; сервис купонов.
- **Цель:** вернуть купон из статуса E в A или D.
- **Предусловия:** купон в статусе E; есть запрос менеджера.
- **Триггер:** запрос менеджера на разбор купона в статусе E.
- **Основной поток:**
  1. Сотрудник поддержки открывает купон в статусе E.
  2. Выбирает целевой статус (A или D).
  3. Сервис переводит купон из E в выбранный статус (правила перехода — см. [раздел 7](#7-бизнес-правила-и-статусная-модель)).
  4. Сервис логирует операцию в журнале событий по купонам, персональные данные не фиксируются.
  5. Сервис подтверждает результат.
- **Альтернативные потоки:**
  - A1. Купон не в статусе E. Сервис сообщает, что разбор не требуется - неверный статус.
- **Исключительные потоки:**
  - E1. Недоступность БД / сбой. Транзакция откатывается, статус не меняется; повторный запрос безопасен.
- **Постусловия:** при успехе купон в A или D, операция залогирована; при отказе - статус не изменён.

- **Связанные требования:** [ФТ-7](#фт-7-разбор-статуса-ошибка), [ФТ-10](#фт-10-логирование-событий) UC: [UC-3](#uc-3-гашение-купона).

### UC-9. Загрузка акций

- **Акторы:** система акций - основной; data engineers - участник; сервис купонов.
- **Цель:** получить акции, ТТ и даты их действия из системы акций.
- **Предусловия:** ETL-процесс настроен и запущен.
- **Триггер:** плановая загрузка каждые 15 минут.
- **Основной поток:**
  1. ETL-процесс передаёт пачку данных (акции, ТТ, даты) БД -> БД.
  2. Сервис принимает пачку.
  3. Сервис сохраняет данные в таблицы акций, ТТ и дат.
- **Альтернативные потоки:**
  - A1. Повторная загрузка. ETL повторно передаёт ту же пачку, обработка дублей по правилам (см. [06-assumptions.md](06-assumptions.md), О-3).
- **Исключительные потоки:**
  - E1. Загрузка упала. Фиксируется ошибка; разбор по зонам ответственности (data engineers / команда акций / мы), см. [06-assumptions.md](06-assumptions.md), О-1.
  - E2. Невалидные данные в пачке. Обработка по правилам (см. [06-assumptions.md](06-assumptions.md), О-4).
- **Постусловия:** при успехе данные акций/ТТ/дат сохранены; при сбое данные не загружены (или загружены частично), зафиксирована ошибка.

- **Связанные требования:** [ФТ-8](#фт-8-загрузка-акций) Открытые вопросы: О-1…О-4 в [06-assumptions.md](06-assumptions.md).

### UC-10. Выгрузка в DWH

- **Акторы:** сервис купонов - основной; DWH компании - участник.
- **Цель:** передать в DWH купоны и события по купонам.
- **Предусловия:** DWH доступно; настроены каналы передачи - пачки + Kafka streaming.
- **Триггер:** ежедневная выгрузка, либо потоковая передача изменений.
- **Основной поток:**
  1. Сервис формирует данные для выгрузки - купоны, события.
  2. Сервис передаёт часть данных пачками, часть - через Kafka streaming.
  3. DWH принимает данные.
- **Альтернативные потоки:**
  - A1. Задержка до суток. Данные передаются с допустимой задержкой до суток.
- **Исключительные потоки:**
  - E1. DWH недоступно. Сервис накапливает дельту и передаёт её после восстановления доступности DWH.
- **Постусловия:** при успехе — данные переданы в DWH; при недоступности DWH дельта накоплена, передача выполнена после восстановления.

- **Связанные требования:** [ФТ-9](#фт-9-выгрузка-в-dwh); [НФТ-11](#нфт-11-гарантия-доставки-в-dwh) Открытые вопросы: О-11 в [06-assumptions.md](06-assumptions.md).

## 7. Бизнес-правила и статусная модель

### 7.1. Статусы купона

- **A** - активен.
- **D** - погашен.
- **E** - ошибка.

### 7.2. Разрешённые переходы

- **A-> D** - гашение купона.
- **D -> A** - восстановление купона.
- **A -> E, D -> E** - переход в статус ошибки при неудачной операции. Например, обрыв соединения, недоступность БД.
- **E -> A, E -> D** - ручной разбор статуса ошибки сотрудником поддержки по запросу менеджера.

### 7.3. Запрещённые переходы и условия, при которых переход невозможен

- **D -> D** -повторное гашение погашенного купона - запрещён: система возвращает ответ «погасить нельзя» и логирует попытку.
- Гашение и восстановление после окончания срока действия акции запрещены.
- Гашение и восстановление по отменённой акции запрещены.

### 7.4. Права на операции

- **Разбор E** - только сотрудник поддержки по запросу менеджера.
- **Восстановление D -> A** - любой пользователь системы: менеджер, сотрудник поддержки или запрос от кассы.

## 8. Модель данных. Ключевые изменения относительно Oracle

### 8.1. Что сохраняется без изменений

- COUPON, COUPON_EVENT, PROMO, PROMO_STORE - структура сохраняется; маппинг типов - по [НФТ-10](#нфт-10-совместимость-типов).

### 8.2. Что меняется

- **POS_KEY** - используется для ротации ключей: хранит SECRET_KEY_HASH, VALID_FROM, VALID_TO; на каждую кассу может быть несколько записей - текущий и следующий ключ в переходный период. Логика генерации и выдачи - см. [ФТ-5](#фт-5-проверка-и-выдача-ключа-безопасности-кассы) и [UC-6](#uc-6-генерация-ключей).
- **COUPON_EVENT** - справочник EVENT_TYPE расширяется: добавляется новый тип для ручного разбора E. Конкретное название типа - на согласовании (см. [06-assumptions.md](06-assumptions.md), Д-6). Для неудачных попыток гашения используется существующее поле IS_SUCCESS=N (см. [ФТ-3](#фт-3-гашение-купона)).
- **Задача массовой операции** - новая таблица для асинхронной обработки массовых операций (см. [ФТ-6](#фт-6-ручные-массовые-операции-менеджера)). Поля: идентификатор (PK), тип операции, количество купонов, статус: в очереди / выполняется / завершена, результат: успешно/неуспешно с причинами. Инициатор не сохраняется, логин не фиксируется, (см. [ФТ-6](#фт-6-ручные-массовые-операции-менеджера)).
